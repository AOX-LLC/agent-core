# API reference

This is the public surface of `aox_agent_core`: every name in the `__all__` of the
top-level package and of the `models`, `replay`, `tracing`, `approvals`, `audit`,
`evals` and `sync` areas, plus the routing tier configuration that `models` depends on.

The bulleted outlines are generated from the code (kind, signature, first sentence
of the docstring) by `tools/gen_api_docs.py`; the prose around them is written by
hand. To refresh the outlines after changing the code:

```bash
uv run python tools/gen_api_docs.py          # rewrite the blocks
uv run python tools/gen_api_docs.py --check  # exit 1 if docs/api.md is out of date
```

A test runs the check, so a change that touches the public surface fails until the
outlines are regenerated. Never edit between the `api:begin` and `api:end` markers.
A name missing from an outline means it is not in that area's `__all__`: anything
else is internal and may change without notice. Errors live in
`aox_agent_core.errors`, rooted at `AgentCoreError`; the storage helpers
(`open_database`, `install_postgres_schema`) live in `aox_agent_core.storage`.

## The pieces and how they fit

- **Models and routing** make a call: `AgentClient` picks a tier, sends the request
  and returns a `CallResult` with usage and cost.
- **Replay** answers that call from a committed recording instead of the network, so
  tests and examples need no key.
- **Tracing** puts one OpenTelemetry span on each call.
- **Approvals** gate an action behind a human decision; **audit** is the append-only
  log that every approval step writes to, and that your own code can write to.
- **Evals** run a fixture suite through a target (usually a model call) and score it.
- **Sync** wraps the async audit log and approval queue for scripts.

The library authenticates nobody. Your application builds a `Principal` from its own
session and passes it in; the library decides what that principal may do.

## Model client

`AgentClient` is the entry point and `ModelClient` is the protocol a host should
type its dependency as, so a test double with the same `call` can stand in. Use
`await client.call(...)` in async code and `client.call_sync(...)` only in scripts;
`call_sync` raises `EventLoopRunningError` inside a running event loop.

Pass `output=SomeModel` for a validated instance of that Pydantic model. A response
that fails validation is sent again, up to `max_attempts` tries in all; with
`routing.escalate_on_structured_failure` set the call then moves up one tier. A
refusal raises `ModelRefusalError` at once. Usage and cost in the result cover every
attempt. A `PromptRef` carries its own system prompt, so `system` must be `None` with
one.

```python
client = AgentClient(load_config(Path("agent-core.toml")))
result = client.call_sync(PROMPT, inputs={"currency": "USD"}, output=Fields, task="extraction")
print(result.output, result.cost_usd, result.trace_id)
```

## Routing

Routing is `models.router` (exported through `aox_agent_core.models`) plus the tier
configuration in `aox_agent_core.config`. A call names a tier or a task, never both;
with neither, `routing.default_tier` is used. `ConfigRouter` is the default `Router`.
It maps a task to a tier through `routing.tasks`, estimates the worst-case cost
(input plus the maximum output tokens, at the tier's prices) and compares it with
`routing.budget_usd_per_call`. When that is over, `routing.on_budget_exceeded`
decides: `RAISE` raises `BudgetExceededError`; `DROP_ONE_TIER` tries the next cheaper
tier once and raises only if that is still over budget or there is none.
`RouteDecision.requested_tier` differs from `tier` when a tier was dropped, and its
`reason` says why. A retry or escalation that could take the total over budget is
refused rather than sent.

PDF pages are counted from the file's bytes, which is best effort: set
`routing.count_pdf_pages` to false when PDFs come from untrusted users and every PDF
is budgeted at the API's 100-page limit.

## Replay

In `REPLAY` mode the client uses `ReplayProvider` and never contacts a provider. In
`RECORD` mode it calls the live provider through `RecordingProvider`, which writes one
JSON file per exchange under `replay.cassette_dir`; recording a key again replaces its
file. A call made with a `PromptRef` is keyed by content (`replay_key`): prompt id and
version, routed tier, output schema name, normalized inputs, attachment SHA-256s and
attempt number. The model id, run ids, timestamps and call order are not in the key,
so a recording made on one model replays on another. A call without a `PromptRef` is
keyed by `request_hash`, with repeated identical requests told apart by a sequence
number.

A miss raises `ReplayMissError`, which names the key and the file it looked for. A
recording whose template, system prompt or schema has changed raises
`StaleRecordingError`. Recordings are meant to be committed; the store scans them for
secrets with a `Scrubber` before writing and refuses by default
(`SecretInRecordingError`). The recording format is version `RECORDING_FORMAT_VERSION`
and the keys and file names are stable public API.

## Tracing

The library only uses the OpenTelemetry API and never configures an exporter: until
your application sets up the SDK, spans record nothing. Each call is one span named
`agent_core.model_call`, and `CallResult.trace_id` is set when a trace is recording.
The span and attribute names in `aox_agent_core.tracing.attributes` (`gen_ai.*`
following the OpenTelemetry GenAI conventions, `agent_core.*` for the rest, such as
`agent_core.cost_usd`, `agent_core.tier` and `agent_core.run_id`) are public API
because dashboards depend on them. No attribute carries a credential, a header, or
prompt or completion text; content capture is opt-in (`TracingConfig.capture_content`)
and goes through the secret scrubber first.

## Approvals

An approval is one human decision for one run of one action. The flow is
`submit` (the requester, usually an agent), `resolve` (a human with the required
role), then `consume` (the requester, right before acting). `consume` atomically moves
an approved request to `CONSUMED`, so an approval authorizes a single run, and it
checks that the action and payload equal what was approved: the request stores the
SHA-256 of the canonical JSON of `{"action": ..., "payload": ...}`
(`approval_payload_hash`). The `summary` is free text the requester wrote and is not
bound by that hash; never decide from it alone. Store the payload itself with
`include_payload=True` so an approver can see what the hash binds.

`RoleApproverPolicy` is the default policy, and `resolve` calls it itself, so a caller
cannot skip it. A principal may resolve a request only if it is human, the action is
in `roles_by_action` with the same role the request stored, the principal holds that
role, it is neither the requester nor a named delegate, and the request is pending
and unexpired. Each refusal is a `DenialReason`, written to the audit log. The role an
action needs is decided on the approver side, because the requester writes
`required_role` when it submits. `trust_requester_role=True` takes the requester's
word instead; it is for local development and must never be used where the requester
may be compromised.

Submitting is idempotent per requester, action and payload hash: a repeat with the
same terms returns the open request, and one that differs raises
`ApprovalConflictError`. Requests live at most `TTL_SECONDS_MAX` seconds; expiry is
judged from `expires_at` on every read, whether or not `expire_due` has run.

```python
policy = RoleApproverPolicy(roles_by_action={"invoice.pay": "ops.approver"})
queue = SQLApprovalQueue(database, audit_log=log, policy=policy)
request = await queue.submit(
    action="invoice.pay",
    summary="Pay invoice INV-1042",
    payload=payload,
    requested_by=agent,
    required_role="ops.approver",
    ttl_seconds=3_600,
)
await queue.resolve(request.id, decision=Decision.APPROVE, principal=human)
await queue.consume(request.id, action="invoice.pay", payload=payload, principal=agent)
```

`examples/approval_flow.py` runs this end to end after a routed call.

### Trust notes

- **SQLite is not a trust boundary.** A SQLite queue has no roles, so it acts for
  `ApprovalSide.BOTH`, and the library's own checks (the policy, the compare-and-set
  updates, the audit trail) are all there is. Anyone who can write the database file
  is trusted with everything, including approving a request. Use it for development,
  tests and single-user scripts.
- **On Postgres the database enforces it, if the owner installs it.** The owner role
  runs `install_postgres_schema` (never the application), naming a requester role
  (submit, consume, cancel) and an approver role (approve, reject). A guard trigger
  then checks every insert and update against the allowed transitions, using the
  database's own clock and role membership, so the requester role cannot
  move a request to approved by any route, plain SQL included. Without that installer
  run, none of this holds. The application connects as the requester or the approver
  role, never the owner.
- **Login binding is opt-in.** `install_postgres_schema(bind_resolved_by=True)` makes
  the guard refuse a decision whose `resolved_by` is not the principal the owner
  mapped to the deciding login. It is off by default, because a host whose approvers
  share one login cannot use it.
- **The library authorizes; it does not authenticate.** If the application hands it a
  forged `Principal`, the library trusts it. Postgres roles bind the database
  connection, not the claimed principal id, unless login binding is on.

## Audit

`AuditLog` is an append-only, hash-chained log: each record carries the hash of the
previous one, so editing or removing a record breaks the chain. Both backends refuse
`UPDATE` and `DELETE` with triggers (and `TRUNCATE` on Postgres), and on Postgres the
application role may only `INSERT` and `SELECT`. The approval queue writes an audit
event for every submission, resolution and denied attempt, in the same transaction as
the change when the queue and the log share a database.

Payloads must be small JSON metadata: ids, counts, hashes, reason codes. Keys ending
in `FORBIDDEN_KEY_SUFFIXES` (for example `secret`, `token`, `password`) are rejected,
floats are rejected (write costs as decimal strings), and payload strings are scanned
for secrets. Never put prompt or completion text or personal data in a payload; record
a hash and a reference.

### What verification does and does not prove

`verify()` walks the whole chain and raises `AuditIntegrityError` at the first
mismatch. `SQLAuditLog.verify_report()` keeps walking and returns a `VerifyReport`
listing every problem. The chain alone proves nothing against someone who can rewrite
rows, because they can rebuild every hash after the edit. Only a head kept somewhere
the log's writers cannot reach (`head()`, stored elsewhere and passed back as
`expected_head`) shows that the log has not been rewritten or cut short since. On
SQLite, anyone who can write the file can also drop the triggers. On Postgres, an
owner or superuser can; the chain detects that, but only against an external head.

## Sync facade

`SyncAuditLog` and `SyncApprovalQueue` wrap an async log or queue for scripts that
have no event loop of their own. Each wrapper runs its calls on one background thread
with its own event loop, so a connection pool opened by the first call serves every
later one; `close()` (or the context manager) shuts it down. Calling a facade from
inside a running event loop raises `EventLoopRunningError`: await the async object
instead. The facades take no `connection=`, because a host transaction belongs to the
loop that owns the connection. They add no safety of their own: the trust notes above
apply unchanged.
